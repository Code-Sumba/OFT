Database Schema and Common Queries

The six PostgreSQL tables, how they relate, how they mirror the blockchain, and ready-to-use SQL for support and debugging.

ForDevelopers and support staff

Sourcedb/schema.sql

01Role of the database

The blockchain is the source of truth for batch history. The database holds:

  • A fast cache of chain state: batches, events and certificates, written only by applying contract events.
  • Off-chain data: users and password hashes, quantities and units, fraud alerts, indexer progress.

Batch history can be rebuilt from chain events by re-indexing. Users can't be, so back the database up. The schema is in db/schema.sql and is applied with npm run db:migrate. Every statement uses IF NOT EXISTS, so it is safe to run again.

batch_events

One row per applied contract event. event_type: registered, certified, rejected, transferred, sold. UNIQUE (tx_hash, log_index) makes re-applying an event harmless. Index: (batch_code, block_number).

certificates

The full certification history: every approve or reject decision, with its CID, expiry and certifier. UNIQUE (tx_hash).

fraud_alerts

Rule violations from the fraud engine. rule R1–R5; severity medium or high; resolved is set automatically when the rule clears, or when an admin dismisses the alert. At most one open alert per (batch, rule). Index: (resolved, severity).

indexer_state

A single row (id = 1) holding last_block, the last block the indexer finished. It is created as DEPLOY_BLOCK − 1 on first run.

Indexes

idx_batches_farmer, idx_batches_owner, idx_batch_events_code_block, idx_fraud_alerts_open, plus the unique constraints above.

05Common queries

Read-only first

These are for support and debugging. Never UPDATE batch, event or certificate rows by hand: the fraud engine will flag the batch as not matching the blockchain (R2). Change data only through the app.

Accounts waiting for approval

SELECT name, email, role, organisation, created_at
FROM users WHERE status = 'pending' ORDER BY created_at;

Find a batch and who holds it

SELECT b.batch_code, b.product, b.status, b.stage, b.trust_score,
       f.name AS farmer, o.name AS holder, o.role AS holder_role
FROM batches b
JOIN users f ON f.id = b.farmer_id
JOIN users o ON o.id = b.current_owner_id
WHERE b.batch_code = 'OT-2026-4QNEHY';

Full journey of a batch

SELECT e.event_time, e.event_type, e.stage, e.location,
       fu.name AS from_user, tu.name AS to_user, e.tx_hash
FROM batch_events e
LEFT JOIN users fu ON fu.id = e.from_user_id
LEFT JOIN users tu ON tu.id = e.to_user_id
WHERE e.batch_code = 'OT-2026-4QNEHY'
ORDER BY e.block_number, e.log_index;

Batches still waiting for the blockchain (sent but not confirmed)

SELECT batch_code, product, tx_hash_register, created_at
FROM batches WHERE last_block = 0 ORDER BY created_at;

Batches waiting for a certifier

SELECT batch_code, product, origin, created_at
FROM batches WHERE status = 'registered' AND last_block > 0 ORDER BY created_at;

Certificates expiring in the next 30 days

SELECT batch_code, product, stage, cert_expiry
FROM batches
WHERE status = 'certified' AND stage <> 'sold'
  AND cert_expiry BETWEEN now() AND now() + interval '30 days'
ORDER BY cert_expiry;

Open fraud alerts with their batch

SELECT a.created_at, a.rule, a.severity, a.batch_code, b.product, b.trust_score, a.details
FROM fraud_alerts a JOIN batches b ON b.batch_code = a.batch_code
WHERE a.resolved = false ORDER BY a.severity DESC, a.created_at DESC;

Batches per stage and average trust score

SELECT stage, COUNT(*) AS batches, ROUND(AVG(trust_score)) AS avg_trust
FROM batches GROUP BY stage ORDER BY batches DESC;

A farmer's batches

SELECT b.batch_code, b.product, b.quantity, b.unit, b.status, b.stage, b.trust_score
FROM batches b JOIN users u ON u.id = b.farmer_id
WHERE u.email = 'farmer@demo.local' ORDER BY b.created_at DESC;

Certification decisions by each certifier

SELECT u.name, COUNT(*) FILTER (WHERE c.approved) AS approved,
       COUNT(*) FILTER (WHERE NOT c.approved) AS rejected
FROM certificates c JOIN users u ON u.id = c.certifier_id
GROUP BY u.name;

Activity per day (last 14 days)

SELECT date_trunc('day', event_time)::date AS day, event_type, COUNT(*)
FROM batch_events WHERE event_time > now() - interval '14 days'
GROUP BY 1, 2 ORDER BY 1, 2;

How far the indexer has got

SELECT last_block FROM indexer_state WHERE id = 1;

Make the indexer re-read from a block (for example after restoring a backup)

UPDATE indexer_state SET last_block = 49793126 WHERE id = 1;  -- deploy block − 1

This is safe: re-applying events changes nothing that is already correct, and fills in anything missing.

Approve or block a user by email (same as the admin panel)

UPDATE users SET status = 'approved' WHERE email = 'person@example.com';

Reset a password

-- hash created with: node -e "console.log(require('bcryptjs').hashSync('NewPassword', 10))"
UPDATE users SET password_hash = '$2b$10$…' WHERE email = 'person@example.com';

06Backups and resets

  • Backups: turn on Supabase daily backups. For a manual copy: pg_dump "$DATABASE_URL" > organic-trace.sql.
  • After restoring an older backup: set indexer_state.last_block to the deploy block − 1, as above, so missing chain events are re-applied.
  • Full reset (development only): drop and recreate the database, run db:migrate and db:seed, and set DEPLOY_BLOCK to the current block. Old on-chain batches unknown to the new database are skipped by the indexer.
