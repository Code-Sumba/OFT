01Context and goals

Organic Trace lets several organisations that don't fully trust each other (farmers, certifiers, processors, distributors, retailers) share one tamper-evident record of each produce batch. Shoppers check that record by scanning a QR code. The design goals, taken from the PRD:

  • Integrity: the blockchain is the source of truth, and any difference between the database and the chain is detected.
  • Usability: participants use an email and password, never a crypto wallet; shoppers need no login.
  • Cost: keep on-chain data minimal (identifiers, short fields, certificate CIDs) and measure the saving.
  • Reliability: no lost or duplicated records when the network is slow or a process restarts.

05Data flows

5.1 Registering a batch

  1. Website → POST /api/upload (certificate) → type checked from the file's bytes → Pinata → returns the CID.
  2. Website → POST /api/batches. The API validates the input and inserts the database row first, which reserves a unique batch code.
  3. The relayer sends registerBatch(code, product, origin, harvestDate, farmerActorId, cid), and the transaction hash is stored straight away.
  4. On confirmation, the BatchRegistered event is applied: last_block is set, a registered event row is added, and the trust score is computed (60 until certified).
  5. If the contract rejects the call, the reserved row is deleted and the user gets 4xx. If confirmation times out, the API answers 202 and the indexer completes it.

5.2 Certifying, transferring, selling

Same pattern: API checks → relayer transaction → contract checks → events applied → trust recomputed. The certifier's on-chain id is passed explicitly (certifierId), so each certification is attributed even though the relayer signs it.

5.3 Public verification

  1. The shopper opens /trace/<code>. Next.js renders the page shell at once, and the verification streams in.
  2. The server sends GET /api/trace/:code to the API, passing on the visitor's address for rate limiting.
  3. TrustService.recompute loads the batch and events, compares them with getBatch and getHistory on the chain (2.5-second timeout, 30-second cache), evaluates R1–R5, stores the score, and syncs alerts.
  4. The response contains the batch, timeline, certificates, trust result, verification (matches chain, differences) and the contract address.

06Consistency between chain and database

  • Two writers, one result: the API (right after confirmation) and the indexer (later) both call applyEvents.
  • No duplicates: batch_events is unique on (tx_hash, log_index); certificates on tx_hash. Inserts use ON CONFLICT DO NOTHING.
  • No rollback: batch state is updated only when (block, logIndex) is newer than the stored (last_block, last_log_index).
  • Resumable: indexer_state.last_block is saved after each chunk of up to 1,000 blocks; the indexer stays 2 blocks behind the head to avoid re-organisations.
  • Final guard: even if the database is wrong, the contract refuses invalid moves (tested: "a stale database still cannot skip a stage").
  • Detection: rule R2 compares the two on every trace look-up.

07Fraud engine

evaluateBatch is a pure function (facts in, score out), which makes it easy to test. TrustService collects the facts (status, expiry, transfer times, chain comparison), stores the score, and keeps fraud_alerts in step: one open alert per batch and rule, closed automatically when the rule clears. R2 alerts stay open if the chain couldn't be checked.

RuleConditionImpactSeverity
R1status = registered−40high
R2database differs from chain (fields, owner or any hand-over)−30high
R3certified and expiry < now−25high
R4more than 3 transfers in any sliding 60-minute window−10 each, max −20medium
R5status = rejected (replaces R1)−60high

08Security design

ThreatControl
Stolen passwordsbcrypt (10 rounds); same 401 and timing for unknown emails and wrong passwords; failed-login rate limit.
Session theft (XSS)JWT in an HTTP-only cookie (Secure in production); React escapes output; Helmet headers.
CSRFSameSite=Lax cookie; CORS limited to the site's own origin; same-origin /api forwarding.
Privilege abuseRole and holder checks on every route; the user is reloaded on every request (blocking is immediate); admins can't be self-registered.
Database tamperingR2 detection; the contract as final guard.
SQL injectionParameterised queries only.
Malicious uploads5 MB limit, file type checked from content, a fixed list of types, uploads limited to two roles.
Abuse / scrapingPer-visitor rate limits; the real visitor address is forwarded; the API isn't exposed.
Relayer key compromiseKey only in the server environment; role can be revoked and moved to a new wallet; every action is public.
MisconfigurationConfiguration validated by Zod at start-up; production refuses a localhost site URL.
Data exposurePublic endpoints never return emails; on-chain ids are hashes, not names.

11Deployment view

Three containers from two images: web (the only published port, 3000), api (internal port 4000, with a health check on /api/health) and indexer (same image as api, different command). External services: Supabase PostgreSQL, Pinata, and a Polygon RPC. HTTPS is handled by the reverse proxy. See Document 2.
